## 1. 风险覆盖、行为覆盖和联合覆盖的正式语义

### 1.1 产品 SPEC 要求

- `G-02`：**分别**度量风险覆盖和行为覆盖，并用**同一 Episode 的证据**建立二者的**联合覆盖关系**。
- §5.2：风险覆盖至少允许表达风险分类与具体风险目标、前置条件、身份/授权/策略上下文、风险载体与影响对象、暴露阶段（仅表达/已尝试/被阻断/部分实现/已实现）、关键风险里程碑及其结果、预期风险与意外风险、已观察副作用与不确定性。
- §5.3：必须建立联合单元 `行为路径或状态转移 × 风险类型/目标 × 风险阶段 × 授权上下文 × 执行结果`；**必须保留四种结果**：仅新行为 / 仅新风险 / 新行为与新风险形成新联合关系 / 均无新增。
- `AC-02`：三种覆盖具有稳定、可解释、**可从保存证据重新计算**的标识。
- `AC-03`：能分别识别四类结果。
- §5.4：反馈必须同时包含**行为缺口、风险缺口、联合覆盖缺口、重复或饱和信号以及证据置信度**；不得用不可拆解的总分掩盖某一维度退化。

### 1.2 当前代码事实

**【事实】**（`E2`/`E3`）

- 三者都有**数据结构**：`V2CoverageDelta` 有 11 个"新增项"字段（`coverage/v2_episode_coverage.py:193-212`），含 `new_behavior_risk_links`（联合链接）与 `new_risk_facets`（风险侧面）；快照按 `snapshot_digest` 内容寻址，可从保存证据重算。
- **联合覆盖字段零消费者**：`new_behavior_risk_links`、`new_risk_facets`、`new_risk_objectives`、`new_primary_scheduling_families` 在 `src/` 内**没有任何读取点**（`grep` 计数为 0）。详见 `episode-data-flow.md` §9.4。
- **四类结果被压成一个布尔值**：`_coverage_gain(delta, facts) -> bool` 是一个四路 `or`（`v2_real_runtime.py:1158-1170`），结果传给 `record_valid_episode(..., coverage_gain=...)`。SPEC §5.3 明文写"**不能只输出一个 `coverage_gain` 布尔值**"——当前函数名与语义与该禁止条款逐字对应。
- **风险维度只有两个标量**：`RiskType`（固定 4 值枚举，`v2_seed_pools.py:19-25`）与 `RiskProgressLevel`（0-3 四级，[:28-41](src/sandbox/fuzzer/v2_seed_pools.py#L28-L41)）。SPEC §5.2 列举的 8 类表达中，只有"暴露阶段"由 `RiskProgressLevel` 部分承接，"里程碑结果"由 `new_milestone_outcome_bits` 承接，"意外风险"由 `new_unexpected_violations` 承接；**风险目标**（`new_risk_objectives`）无消费者。
- **没有父样本权重**：`SelectionPolicy` 只有一个取值 `RANDOM_UNIFORM`（`v2_selection.py:20-21`），验证器强制单位权重（[:72-75](src/sandbox/fuzzer/v2_selection.py#L72-L75)）。`WeightedSelectionOption.weight`、`total_weight`、加权游标等结构存在，但**不存在任何非均匀策略**。

**【事实】** 分类法标识是硬编码字符串 `"office-v2-risk-taxonomy-schema-v1"`（`coverage/v2_contracts.py:72`），而仓库中另有一个未被任何代码引用的 `config/risk-taxonomy.yaml`。

### 1.3 差异为什么重要

**【事实】** SPEC 把联合覆盖定位为产品的核心创新点：它要回答"某类风险是**通过哪条行为路径、在什么上下文和阶段**被触达或阻断的"。行为覆盖和风险覆盖各自单独看都可能"看起来在增长"，但只有联合单元能说明二者是否真的咬合。

**【推断】** 当前实现下，系统能回答"这一代新增了几个行为特征"和"某个风险类型推进到了第几级"，**不能**回答"这次的风险是通过哪条路径达成的"。这意味着项目最核心的可解释性主张在数据层有素材、在决策与报告层为空白。

**【事实】** 四类结果的区分不是形式要求：它是 §5.4"不得用不可拆解的总分掩盖某一维度退化"的前提。当前无法区分"这一代无新增"与"这一代只有行为新增但风险无进展"——而后者恰恰是"模式坍缩"的信号（SPEC §1 定义的第二个核心问题）。

### 1.4 不处理的影响

- `AC-02`、`AC-03` 无法满足，`G-02` 停留在 `PARTIAL`；
- `FR-EXP-05` 要求报告的"联合覆盖增长曲线"**没有数据源**，第 7 项的实验报告无法完整；
- 第 2 项（覆盖反馈进入下一代）中"针对联合缺口选择"**没有可用的缺口表达**——即使决定要改，也需要先有本项定义的联合语义；
- 风险覆盖若长期停留在 4 值枚举 + 4 级标量，`G-02` 的"风险覆盖"与"风险类型轮转"难以区分。

**【推断】** 因此本项是第 2 项、第 7 项的前置。

## 2. 覆盖反馈如何进入下一代

### 2.1 产品 SPEC 要求

- `FR-FUZZ-01`：闭环中"反馈**必须实际影响**下一轮父样本选择、目标方向或变异内容。**仅在 Episode 完成后计算覆盖率或决定是否保存结果，不构成完整的覆盖率引导模糊测试**。"
- `FR-EXP-02`：`coverage_guided` "读取历史双重覆盖反馈，**针对风险、行为和联合覆盖缺口**选择父样本**及变异方向**，并记录'为什么选择'"。
- §5.4：反馈必须**同时**包含行为缺口、风险缺口、联合覆盖缺口、重复或饱和信号以及证据置信度；调度器"可以采用分层、多目标或 Pareto 等策略，但必须保留各维度的可解释性；不得用不可拆解的总分掩盖某一维度退化"。
- `FR-FUZZ-05`：种子晋升、**父样本权重**、重复降权和长尾探索必须能追溯到具体覆盖证据。
- `AC-04`：引导模式的历史反馈**确实影响**后续选择或变异，并有**可审计的选择理由**。

### 2.2 当前代码事实

**【事实】**（`E3`）

- 反馈对象**被完整构造**：`NextGenerationFeedback`、`FeedbackBrief`、`FeedbackGapKind`（6 个取值）、guidance codes（`v2_feedback.py`），并被持久化。
- 但 `decide_next_generation` 接收 `latest_feedback` 后**只用于两件事**：校验（"next generation requires latest feedback"、代次一致性，`v2_orchestrator.py:108-115`）与记录 `input_feedback_digest`（[:143-151](src/sandbox/fuzzer/v2_orchestrator.py#L143-L151)）。**它不把 feedback 传给** `choose_next_allocation`（[:116-121](src/sandbox/fuzzer/v2_orchestrator.py#L116-L121)）。
- 真正影响下一轮的只有 `state.risk_progress`：`choose_next_allocation` 无条件传入 `progress_states=state.risk_progress`（`v2_campaign_loop.py:373`），`select_risk_pool_seed` 用 `min(progress)` 过滤风险池后再均匀抽取（`v2_risk_pool_scheduler.py:118-133`）。
- **变异方向不受覆盖反馈影响**：`independent_uniform_selection` 是唯一的选择原语，三个调用点（风险方向、父样本、算子数量/族/变体）全部均匀（`mutation/v2_policy.py:472,485,497`），其 RNG 输入字典中**不含任何覆盖摘要**。
- **父样本权重不存在**（见第 1.2 节）。
- **饱和信号不生效**：`allow_coverage_saturation=False`（`v2_real_runtime.py:734-742`），代码注释说明这是有意的——"Coverage feedback can guide selection, but must not silently shorten a Campaign after a run of low-gain Episodes"。
- **可审计性 ✅**：`reason_codes`、`SelectionReceipt.reason_codes`、`RiskPoolSelection.reasons`、`score_components` 均存在且带内容摘要。

### 2.3 差异为什么重要

**【事实】** SPEC 对"覆盖率引导"的定义是**行为性**的：反馈必须改变选择或变异。当前实现中，反馈对象的**内容**（行为缺口、联合缺口、饱和信号、置信度）不参与任何决策；只有它的一个**标量投影**（风险进度）参与，且只参与"选哪个风险池"。

**【推断】** 因此当前实现更准确的描述是"**风险类型均衡轮转 + 池内均匀采样**"，而不是"覆盖率引导的语义模糊测试"。这不等于否定当前实现——风险进度确实来自 Episode 证据，确实构成一条反馈通道——但它与 SPEC 所主张的机制强度有实质差距。

**【事实】** `min(progress)` 过滤的语义是**均衡**（把预算摊到进度最低的类型），而不是**探索**（往缺口最大的方向走）。这两者在早期可能表现相似，但在中后期会产生不同行为：均衡会把所有类型拉到同一水平，探索会持续深挖回报最高的方向。

### 2.4 不处理的影响

- `G-03`、`FR-FUZZ-01`、`FR-EXP-02`、`AC-04`、`FR-FUZZ-05` 均停留在 `PARTIAL`；
- 第 3 项（随机基线公平性）中"引导模式的优势来源"无法界定——若引导模式的唯一额外机制是晋升与去重，那么实验测得的差异来自"语料库增长"，而不是"覆盖反馈引导"；**这会直接影响实验结论的可解释性**；
- `FR-EXP-05` 报告的"覆盖效率"曲线无法归因到具体机制。

**【推断】** 本项与第 1 项、第 3 项构成一个依赖三角：第 1 项决定"缺口怎么表达"，本项决定"缺口怎么被消费"，第 3 项决定"对照组是否公平"。三者需要一起讨论，否则单独改任一项都无法得到可解释的实验。

### 2.5 可选方向及取舍

| 方向 | 内容 | 取舍 |
|---|---|---|
| **A. 明确降级为"风险均衡基线"** | 承认当前机制，修改 SPEC 措辞，把"覆盖率引导"重新定义为"基于风险进度的均衡调度" | 与 `AGENTS.md` §2 冲突（不得为迎合代码而缩窄规格）；但若用户的真实目标就是风险类型覆盖的均衡性，这是诚实的表述 |
| **B. 只把 `risk_progress` 的语义讲清楚** | 不改机制，但在报告与文档中明确"反馈 = 风险类型进度标量"，并把 `feedback` 对象降级为审计记录 | 成本最低、立刻消除"名字暗示了不存在的机制"的误导；但 `AC-04` 仍只能勉强满足，`FR-EXP-02` 的"行为/联合缺口"仍缺失 |
| **C. 把反馈对象真正接入选择** | 让 `NextGenerationFeedback` 的缺口信息参与父样本选择（引入加权/分层/Pareto 策略，替代强制单位权重） | 直接满足 `FR-FUZZ-01`/`FR-EXP-02`/`FR-FUZZ-05`；但引入"权重从哪来""如何保持可解释""如何避免总分掩盖退化"等新设计问题，且需要 SPEC §15 已列为待决的"多目标调度的选择算法以及稀有度、饱和度和语料晋升策略" |
| **D. 饱和信号单独接入** | 只让 `allow_coverage_saturation` 类信号参与终止判定（恢复 `SATURATED` 的语义），其余保持 | 小步、影响面窄；但 SPEC §5.4 要求的是**五类**反馈同时存在，只接入一类仍然不完整；且当前注释明确说明关闭饱和是有意的，需要先确认那个意图 |

**共同前置**：方向 C 需要先决定"**可解释性如何保证**"——SPEC §5.4 禁止"不可拆解的总分"。若引入加权，必须同时定义各维度如何单独报告。这也是 SPEC §15 的待决事项。

### 2.6 推荐方向及理由

**【建议】** 倾向 **先 B 后 C**，理由：

1. **B 的成本极低且消除一个真实的误导风险。** 当前 `NextGenerationFeedback` 的名字与结构暗示它驱动了下一代，实际没有。无论最终选哪个方向，先把"反馈实际是什么"讲清楚都是必要的，且不涉及代码语义变更；
2. **C 需要先解决 §5.4 的可解释性约束**，而这依赖第 1 项冻结的缺口语义。在联合缺口没有正式表达之前引入加权选择，很可能得到另一个"看起来像覆盖引导"的机制；

## 3. 随机基线的公平性

### 3.1 产品 SPEC 要求

- `FR-EXP-01`：`random_independent` "从同一合法候选空间中独立采样，拥有与引导模式相同的语义变异能力，**但不得读取之前 Episode 的覆盖快照、缺口、晋升结果或其他跨 Episode 反馈来影响下一轮选择**。"
- `FR-EXP-03`：两种模式比较时须冻结并保持一致 8 类条件，其中包含"Scenario、初始状态和**合法候选空间**"，并明确"**唯一原则性差异应是：是否消费跨 Episode 覆盖反馈来影响后续探索**。随机模式不能使用更弱的模型、更窄的候选空间或更差的错误处理。"
- `AC-05`：随机模式不消费跨 Episode 覆盖反馈，且与引导模式满足公平性约束。
- §3：核心研究假设必须在"Agent、模型、场景、合法候选空间、语义变异能力、执行环境、Oracle 和资源预算一致"时成立。
- §12 非目标：**不得"为证明预设结论而调整随机基线、隐藏失败或事后更换指标"**。

### 3.2 当前代码事实

**【事实】**（`E3`，四步逐行核对，详见 `strategy-comparison.md` §4）

1. 结算时 `settle_risk_progress(...)` **无策略判断**（`v2_real_runtime.py:751-756`），由本 Episode 的 `behavior_assessment`（基于 Oracle 与覆盖输入）推进该风险类型等级，**单调只升不降**（`v2_campaign_state.py:295-335`）；
2. 下一代分配时 `progress_states=state.risk_progress` **无策略判断**（`v2_campaign_loop.py:373`），`include_derived=not independent` 是该调用中**唯一**的策略相关实参；
3. `select_risk_pool_seed` 用 `min(progress)` 过滤风险池后再均匀抽取（`v2_risk_pool_scheduler.py:118-133`）。

⇒ **`random_independent` 模式读取消费跨 Episode 覆盖反馈来影响下一轮的风险方向选择。**

**【事实】** 两种模式另有 3 类**非"是否读反馈"**的差异：

| 差异 | 位置 | 效果 |
|---|---|---|
| `include_derived=False` | `v2_campaign_loop.py:377` | 引导模式晋升后父样本池**严格更大** |
| 强制 `NO_PROMOTION` + 不增长目录 | `v2_campaign_loop.py:177-183`、`v2_real_runtime.py:757` | 引导模式语料库增长，随机模式恒定 |
| 三个去重摘要集合 + `candidate_history` 传空 | `v2_real_runtime.py:320-324,346-384` | 引导模式**拒绝重复候选并重试**，随机模式不拒绝 |

**【事实】** 随机模式的所有**显式**守卫都是正确的：不晋升、不改目录、不加载候选历史、不记录反馈摘要（`v2_campaign_store.py:124-128,1097-1101,1613-1616` 甚至有存储层断言强制这些不变式）。

**【事实】** 测试缺口：`tests/` 中引用 `RANDOM_INDEPENDENT` 的**仅 1 个文件**（`test_exploratory_campaign.py`），断言只覆盖 CLI 解析与策略持久化；`"independent-random-baseline-no-promotion"` 等 4 个守卫字符串在 `tests/` 中**零命中**。**没有任何测试断言"随机模式的选择不受历史影响"**。

**【推断】** SPEC `FR-EXP-03` 与 `FR-FUZZ-05` 之间存在**规格内部的张力**：前者要求"唯一原则性差异是是否消费反馈"，后者要求引导模式做种子晋升与语料库增长——而晋升必然改变父样本空间与候选集。这个张力无法只靠改代码消除，需要产品层面裁定。

### 3.3 差异为什么重要

**【事实】** 这是**整个课题的实验有效性前提**。SPEC §3 的核心假设是"在……合法候选空间……一致时，覆盖率引导模式应比随机模式更快发现新的风险—行为组合"。

**【推断】** 当前状态下，两种模式的比较测得的不是"反馈 vs 无反馈"，而是"**较多反馈 + 更大父样本池 + 去重门控 vs 较少反馈 + 固定池 + 无去重**"。因此：

- 若引导模式胜出，**无法归因**是覆盖反馈的功劳，还是仅因为它的搜索空间更大、重复更少；
- 若随机模式胜出或持平，也**无法**据此否定覆盖率引导的价值，因为对照组并不"更弱"——它在风险类型铺开度上其实**更强**（被强制轮转）。

**【事实】** SPEC §12 把"为证明预设结论而调整随机基线"列为**非目标**。当前实现并非有意削弱基线（多处显式守卫表明作者在意公平性），但**净效果**是基线不满足独立性定义。

**【事实】** 这个偏差方向值得注意：`min(progress)` 过滤使随机模式**几乎必然在前 4 个 Episode 覆盖全部 4 个风险类型且不可重复**，而真正的独立采样允许重复。因此偏差**部分有利于基线**——这降低了"有意削弱基线"的可能性，但也说明它不是一个中性的随机对照。

### 3.4 不处理的影响

- `G-04`、`FR-EXP-01`、`FR-EXP-03`、`AC-05` 保持 `CONFLICTING`；
- `AC-06` 的"按冻结协议重复运行配对实验"即使实现了编排，结论仍**不可归因**；
- **最高风险**：若在此状态下运行正式实验并报告"引导模式更优/不优"，该结论在方法学上不成立。而 §12 明确禁止"事后更换指标、删除失败样本或削弱随机基线"——留下这个状态再跑实验，风险高于先修正再跑。

### 3.5 可选方向及取舍

| 方向 | 内容 | 取舍 |
|---|---|---|
| **A. 让随机模式真正独立** | 在随机模式下不把 `risk_progress` 传入选择（例如传空进度状态，使所有池并列），使方向选择纯粹由 `campaign_seed + generation_index` 决定 | 直接闭合 `FR-EXP-01` 的第一半；但**会减少**基线在风险类型铺开度上的优势，即基线会变"更随机"。这是**修正**而非削弱，但需要在实验前声明这一变更 |
| **B. 明确重新定义"独立"** | 承认"风险进度"不属于 SPEC 所指的"覆盖反馈"，在 SPEC 中澄清边界 | 成本最低；但 `risk_progress` 由 Oracle 与行为证据推导、跨 Episode 累积，**符合** SPEC 对"跨 Episode 反馈"的描述，重新定义需要很有说服力的理由，且有"为迎合代码而缩窄规格"之嫌 |
| **C. 让两种模式都读反馈，另设真正的空白基线** | 保留现状作为"引导"的两种强度，另加一个不读任何反馈的第三模式 | 保留现有实现价值；但增加一个模式 = 增加实验臂数与预算，且 `FR-EXP-01` 要求的**就是** `random_independent` 这个模式本身是独立的 |
| **D. 消解规格内部张力：把晋升/去重移出公平性约束** | 在 SPEC 中明确"晋升与语料库增长属于被检验的引导能力，不属于'候选空间不一致'"，同时修正随机模式的 `risk_progress` 消费 | 直接面对 §3.2 指出的规格张力；但需要用户裁定"什么算候选空间一致"——这是产品定义，不是实现细节 |
| **E. A + D 组合** | 既修正 `risk_progress` 消费（A），又在 SPEC 中裁定晋升/去重的归类（D） | 最彻底；改动面包含代码与规格两处 |

### 3.6 推荐方向及理由

**【建议】** 倾向 **方向 E**，理由：

1. **A 部分是明确的缺陷，不是设计选择。** `FR-EXP-01` 是禁止性条款，`risk_progress` 无策略分支地生效看起来更像遗漏（所有**显式**守卫都做对了），而不是有意设计。这一点需要用户确认——如果它其实是有意的，那 `FR-EXP-01` 需要改写；
2. **D 部分是规格与规格之间的张力**，只能在产品层裁定。`FR-FUZZ-05` 要求晋升，`FR-EXP-03` 要求候选空间一致，两者不能同时按字面满足。裁定"晋升属于被检验的能力"是一个**产品主张**，需要用户明确做出；
3. **在 A 与 D 定论前不应运行正式对比实验**，否则会产生不可归因的结论，而 §12 禁止事后更换指标；
4. 方向 B 与 C 不推荐：B 有迎合代码之嫌，C 增加实验臂数却不解决 `random_independent` 本身的定义问题。

**这不构成设计批准。** 若采纳 A，需要独立 SPEC 定义"随机独立性"的可检验断言（并补上当前缺失的测试）。

### 3.7 需要用户决定的具体事项

> **决策 1**：是否认可"`random_independent` 模式当前会读取 `risk_progress` 影响下一轮风险方向选择，因此不满足 `FR-EXP-01` 的独立性定义"这一判定？
>
> **决策 2**：`risk_progress` 被随机模式消费是**有意设计**还是**遗漏**？若是遗漏，是否同意在正式实验前修正？
>
> **决策 3**：如何裁定 `FR-EXP-03`（候选空间一致）与 `FR-FUZZ-05`（引导模式晋升与语料库增长）之间的张力？"种子晋升、语料库增长、候选去重"应被视为**被检验的引导能力**（允许存在），还是**违反公平性的候选空间差异**（必须消除）？
>
> **决策 4**：在决策 2、3 定论前，是否同意**暂不运行**正式配对实验？
>
> **决策 5**：是否需要为"随机独立性"补一条可检验的测试断言（当前测试套件对此无判定力）？

## 5. Replay 的确定性等级

### 5.1 产品 SPEC 要求

- `G-05`：保存足够的状态与指令证据，支持**确定性重放**、问题复现和回归测试。
- `FR-REP-02`：保存足以解释和复核执行的 6 类证据。
- `FR-REP-03`：必须**明确区分**四个重放层级——**轨迹重放**（按已保存的调用与结果重建判断链）、**工具重放**（在恢复的环境状态中重放工具指令）、**状态验证**（验证重放前后状态与预期快照一致）、**重新执行**（重新调用非确定性模型并比较允许的差异）。特别地："**不得把'保存了随机种子'误称为大模型输出逐 Token 确定。**重放结论必须说明确定性边界、外部依赖和允许偏差。"

### 5.2 当前代码事实

**【事实】**（`E3`）

- **证据保存充分且带内容摘要**：`RunManifest` 携带 `prompt_digest`、`initial_state_digest`、`normalized_behavior_trace_digest`、`determinism_config_digest`、`recording_complete`、`incomplete_reason`（`replay/models.py:87-112`）；轨迹经 `TrajectoryStore` 分页追加后原子提交（`replay/manifest.py:90-101`）。这一侧对应 `FR-REP-02`，判 `ALIGNED`。

### 5.3 差异为什么重要

**【事实】** SPEC 对重放的要求重点不在"能不能重放"，而在"**声明你重放到了什么程度**"。四层级的存在意义是防止一种特定的过度声称：把"保存了种子和调用序列"说成"可确定性复现模型输出"。

**【推断】** 当前代码在**能力**上比 SPEC 要求的更丰富（三套模式 + 行为比对 + fork 语义），但在**声明**上是空白的。这造成两个具体后果：

1. 无法回答"某个 Finding 是通过哪个层级复现的"——因为层级没有统一命名；
2. 无法回答"这个重放结论的确定性边界在哪"——因为没有声明产物。

**【事实】** `determinism_config_digest` 字段的存在说明"确定性配置"这一概念已被识别，但它只记录配置的摘要，不构成边界声明。

### 5.4 不处理的影响

- `G-05`、`FR-REP-03`、`FR-REP-04`、`AC-07` 保持 `PARTIAL`；
- 第 7 项的"重放成功率"指标**没有层级可依**（成功率的定义依赖层级）；
- **【推断】** 若在报告或论文中使用"可重放"这一表述，当前缺少支撑其精确含义的契约。

### 5.5 可选方向及取舍

| 方向 | 内容 | 取舍 |
|---|---|---|
| **A. 定义统一的四层级契约并映射现有枚举** | 新增四层级的正式标识，把 `ToolReplayMode`/`ReplayMode`/`ForkSuffixMode` 映射到其中，并新增确定性边界声明字段 | 直接满足 `FR-REP-03`；但需要梳理三套现有枚举之间的正交关系，改动面涉及 replay 包的契约 |
| **B. 只补边界声明，层级命名留待后续** | 先增加"确定性边界/外部依赖/允许偏差"的声明字段，四层级正式化单独立项 | 成本低、直接消除"过度声称"风险（SPEC 最强调的一点）；但 `AC-07` 的"按声明的重放层级"仍缺锚点 |
| **C. 用现有枚举直接对应四层级** | 在文档中声明 `strict`≈轨迹重放、`execute_and_verify`≈工具重放等映射，不改代码 | 零代码成本；但映射是否成立需要逐项验证——三套枚举是否真的覆盖"状态验证"与"重新执行"存疑 |

### 5.6 推荐方向及理由

**【建议】** 倾向 **先 B 后 A**，理由：

1. **B 针对 SPEC 反复强调的那一点**（不得把种子保存误称为逐 Token 确定）。当前这个风险是**实际存在**的：代码里有 `determinism_config_digest`、有 `campaign_seed`，很容易在沟通中被表述为"可确定性复现"。补一个边界声明字段即可消除；
2. **A 需要先梳理三套枚举的正交性**（工具维度 / 严格-实时维度 / fork 维度），这是一个真实的建模工作，不宜与 B 混在一起；
3. **C 风险较高**：在没有逐项验证的情况下声明映射，等于用文档制造 `E4` 级结论来支撑 `AC-07`——而审计 Spec §8 明确"`ALIGNED` 不能只依赖 `E4`"；
4. **D 是唯一能把 `FR-REP-01` 从 `UNVERIFIED` 升级的路径**，但需要 Docker 环境授权，宜作为独立任务。

**这不构成设计批准。**

## 6. Oracle、Controller 与 Judge 的事实权威

### 6.1 产品 SPEC 要求

- `FR-JDG-01`：工具调用、工具结果、状态变化、权限事实、策略结果和**终止原因**优先由**确定性 Oracle** 判定。
- `FR-JDG-02`：LLM-as-Judge **只**用于需要语义判断的事项；**不得改写确定性事实**，也**不得成为高风险结论的唯一证据**。
- `FR-JDG-03`：裁判置信度加固必须包括黄金集回归库、主动学习采样、版本/提示/阈值变化回归、漂移监控、低置信度人工升级、可追溯的 Judge 版本与复核记录。
- `G-06`：逐步建立由黄金集、主动学习、漂移监控和人工复核组成的裁判置信度加固能力。
- `SEC-05`：**Controller 不得替 Agent 伪造**工具调用、授权、状态变化、**提交**或**成功证据**。
- `SEC-04`：每个 Episode 结束后**验证副作用被隔离或清理**；**清理失败必须成为显式测试结果**。
- `AC-09`：所有安全结论可追溯到确定性事实或**明确标识的**语义判断，**不由 Controller 伪造证据**。
- `AC-10`：裁判置信度加固只有全部机制通过**独立验收**后才能标记完成。
- `FR-OPS-02`：超时、容器失败、工具失败、无效变异、Judge 不可用和存储失败必须分类保存，**不得悄悄转成成功**。

### 6.2 当前代码事实

**【事实】**（`E2`/`E3`）

**Oracle 侧**

- Oracle 是规则式实现（`scenarios/office_v2/oracle.py`、`security_oracle.py`、`utility_oracle.py`），有 6 个专门测试文件，输出 `oracle_result` 与 `trace_digest`，产物带 `identities_and_digest_match` 自校验。
- **Oracle 在容器内计算，宿主机侧没有独立重算或交叉验证。** 其正确性完全依赖容器内实现。
- `build_execution_closure_from_oracle` 的 `observed_payload_refs`/`used_payload_refs` **确实**由真实 Oracle 暴露阶段推导（`v2_loop_contracts.py:306-373`，逐行核对）。

**Controller 侧（关键）**

- `ExecutionClosure` 的三个字段由调用方**直接写死**（`v2_real_runtime.py:673-675`）：
  ```python
  submitted=True,
  termination_reason="submit",
  cleanup_confirmed=True,
  ```
- **【事实】准确性说明**：本次逐行核对确认，这三个值**当前是准确的**——`_settle_episode` 只在成功路径被调用，而上游 `V2BehaviorSourceFacts` 的验证器会对非 submit 输入直接 `raise ValueError("coverage requires an explicit submit termination")`（`coverage/v2_input.py:111-177`）。因此**当前不存在伪造**。
- **【事实】机制说明**：一致性由**上游路径**保证，不是由**此处读取**保证。若新增一条不经过该验证器的结算路径，这三个字段会静默变成不实声明**且不会报错**。`cleanup_confirmed` 尤其如此——`SEC-04` 要求"清理失败必须成为显式测试结果"，而闭包**总是**声明清理成功。
- **【事实】** 存在真实的清理动作：`cleanup_interrupted`（`v2_real_episode.py:152`）、`_recover_interrupted_work`（`v2_real_runtime.py:169`）。

**Judge 侧**

- `OllamaTargetPreservationJudge` 是 V2 主链中**唯一**的 Judge，**只**用于目标保持判定（`v2_real_runtime.py:842-843`），**不**参与覆盖提取、Finding 判定或 Oracle 事实。职责边界清晰，符合 `FR-JDG-02` 的前半。
- **保留意见**：目标保持判定**完全**由 Judge 给出，而它是**晋升门控**的输入（`v2_campaign_loop.py:188-191`）。即一个 LLM 判断可以是"样本能否进入语料库"的**唯一**证据来源。
- **【事实】** `--ollama-mode embedded` 时 `target_judge=None`，目标保持不可判定 → 晋升被阻断（不静默降级）。
- **【事实】** Judge 输出**没有置信度字段**，**没有**人工复核入口。
- **【事实】** `FR-JDG-03`/`G-06` 的 6 项加固机制**全部不存在**（全仓 `grep` 无命中）。代码中的 "drift" 全部属于**变异侧**校验（`mutation/v2_validation.py:77-111` 的 identity/authorization/objective drift），与 Judge 漂移监控无关。
- **【事实】** 文档**未**宣称 Judge 已校准：`LOG.md:1488` 把"裁判置信度、黄金集、评分漂移和主动学习"列为后续阶段必须补充项；`LOG.md:1500` 明确"不实现通用分数、置信度"。`docs/SPEC.md` §9.2、§12 自述未完成。**这一纪律被遵守。**

### 6.3 差异为什么重要

**【事实】** SPEC 把"事实权威"分成三层：Oracle 判确定性事实、Judge 判语义、Controller **只**编排而不产出事实。当前有一处**事实由 Controller 层声明**：`submitted` / `termination_reason` / `cleanup_confirmed`。

**【推断】** 这个设计在当前是安全的——因为有上游验证器兜底。但它的安全性是**隐式**的：它依赖"所有成功结算路径都必须经过 `V2BehaviorSourceFacts`"这一不变式，而该不变式**没有被断言或测试**。

**【事实】** 这与 `AC-09`/`SEC-05` 的字面要求（"所有安全结论可追溯到确定性事实"、"Controller 不得伪造……提交或成功证据"）相关：当前答案既不是"违反"（值是对的），也不是"满足"（不是推导的）。这个中间状态需要产品裁定。

**【事实】** 目标保持由 Judge 单独决定且门控晋升，这触及 `FR-JDG-02` 的"不得成为高风险结论的**唯一**证据"。它是否构成"高风险结论"取决于产品定义——`SPEC.md` 没有定义什么是高风险结论。

**【事实】** `FR-JDG-03` 完全缺失是 **SPEC 已承认**的状态，本身不构成隐瞒风险。真正的风险是**未来**：一旦有人给 Judge 加置信度字段或把 Judge 用于更多判定，就需要同时建立验收机制，而 `AC-10` 要求"全部通过独立验收后才能标记完成"。

### 6.4 不处理的影响

- `FR-JDG-01`、`FR-JDG-02`、`SEC-04`、`SEC-05`、`AC-09` 保持 `PARTIAL`；`G-06`、`FR-JDG-03`、`AC-10` 保持 `MISSING`；
- **【推断】** 后果分两类：
  - **当前影响低**：值是对的，运行不会出错；
  - **未来影响中高**：新增结算路径时会出现静默的不实声明，且没有任何测试会失败。`cleanup_confirmed` 是其中最敏感的一个，因为它关联 `SEC-04` 的"副作用隔离"这一安全边界；
- Judge 的门控地位若无明确裁定，`FR-JDG-02` 的合规性会一直是解释性的而非事实性的。

### 6.5 可选方向及取舍

| 方向 | 内容 | 取舍 |
|---|---|---|
| **A. 从 Episode 证据推导三个字段** | 让 `submitted`/`termination_reason`/`cleanup_confirmed` 从 `episode` 对象读取，而不是写死 | 消除隐式依赖；但需要确认 `OfficeV2EpisodeResult` 是否携带这些事实——若不携带，需要先扩展 Episode 结果，改动面较大 |
| **B. 保持写死，但补断言守卫** | 显式断言"到达此处时上游已保证显式 submit"，把隐式不变式变成显式断言并加测试 | 成本低，把隐式变显式；但仍不是"事实由证据推导"，`SEC-05` 字面上仍未满足 |
| **C. A + B** | 既从证据推导，又加断言 | 最彻底；改动面最大 |
| **D. 为 `cleanup_confirmed` 单独建立清理结果记录** | 无论 A/B/C，为清理结果建立独立的显式记录，使 `SEC-04` 的"清理失败必须成为显式测试结果"可满足 | 针对安全边界单独处理；需要定义"清理失败"的判定与保存位置 |
| **E. 明确裁定"高风险结论"的定义，据此决定 Judge 的证据充分性** | 在 SPEC 中定义哪些结论属于高风险；若目标保持属于高风险，则需第二条独立证据 | 直接闭合 `FR-JDG-02` 的解释空间；但需要产品定义，且可能需要新增判定机制 |
| **F. 为 Judge 增加版本与置信度记录** | 即使不做完整 `FR-JDG-03`，先补版本与置信度字段与复核记录 | 满足 `FR-JDG-03` 的"可追溯"一项；但会让人误以为置信度加固已启动，需同时在文档中标注未完成 |

### 6.6 推荐方向及理由

**【建议】** 倾向 **B + D + E**，理由：

1. **B 与 D 成本低且针对最具体的风险**：`cleanup_confirmed` 是唯一直接关联安全边界的硬编码字段，D 让它可被显式记录清理失败；B 把隐式不变式变成会失败的断言，成本极小；
2. **A/C 需要先确认 `OfficeV2EpisodeResult` 是否携带这些事实**——若需扩展 Episode 结果契约，那是一个有连带影响的设计决定，不宜在审计收口阶段顺带做；
3. **E 是纯产品定义**，且不解决它 `FR-JDG-02` 的合规性一直是解释性的。它不需要代码改动即可推进；
4. **F 暂时不做**：在 `FR-JDG-03` 整体未启动时先加字段，容易被误读为"置信度加固已开始"，而 `AC-10` 与 `SPEC.md` §9.2 都强调不得在闭环通过验收前宣称完成。当前文档纪律良好，不宜引入模糊信号。

**这不构成设计批准。**

## 7. 实验指标与"优越性"判定

### 7.1 产品 SPEC 要求

- `FR-EXP-04`：正式比较必须采用**预先冻结、版本化的实验计划**，使用**配对 Campaign** 和**多个随机种子**，并**完整保存**成功、失败、超时和无增益 Episode。
- `FR-EXP-05`：报告至少分别展示 7 类内容——行为/风险/联合覆盖的增长曲线（按 Episode、时间、Token、成本）、达到指定覆盖门槛所需预算、独特 Finding 数量与重复率与连续无增益长度、失败率与超时率与恢复情况与重放成功率、多次运行的均值与离散程度与统计不确定性。
- §7.4：主要优越性依据是**联合覆盖与覆盖效率**；风险覆盖和行为覆盖必须**同时单独报告**；任何综合指标都必须**能拆解回原始维度**。
- §7.4 末："精确重复次数和统计检验方案由具体实验 SPEC 在**看结果前**冻结。"
- `AC-06`：能按冻结协议重复运行配对实验，并**分别报告**……**只有证据支持时才宣称引导模式更优**。
- §3 末：若证据不支持优越性，"系统必须**如实报告**无显著优势、退化或实验无效，不得事后更换指标、删除失败样本或削弱随机基线"。
- `FR-OPS-04`：预算按可解释维度记录，包括 Episode、**模型调用**、Token、**工具调用**、时间和成本。
- §12 非目标：不"以最终回答的单次分数替代行为轨迹、状态和工具证据"。

### 7.2 当前代码事实

**【事实】**（`E3`）

**报告层**（`v2_report.py`，仅 94 行）

### 7.3 差异为什么重要

**【事实】** `AC-06` 要求的是"能按冻结协议**重复运行配对实验**，并**分别报告**……"。当前既没有协议层，也没有计算后的指标层。

**【推断】** 后果的严重性取决于第 3 项：如果随机基线不独立（`CONFLICTING`），那么即使把报告层补全，产出的曲线也**不可归因**。因此**第 3 项是第 7 项的前置**，反之不然——报告层可以在基线问题解决后再补。

**【事实】** `FR-EXP-05` 强调"任何综合指标都必须能拆解回原始维度"，与 §5.4 的"不得用不可拆解的总分掩盖某一维度退化"是同一约束的两处表达。当前报告**没有**综合指标（只有原始计数），所以不存在"掩盖"问题——但也无法支撑优越性判定。

**【事实】** `FR-OPS-04` 缺失的"模型调用/工具调用"维度，在跨模型或跨运行时比较时会成为归一化基准的缺口。

### 7.4 不处理的影响

- `FR-EXP-04`、`FR-EXP-05`、`AC-06`、`FR-OPS-04` 保持 `PARTIAL`；
- **无法产出 `SPEC.md` §7.4 要求的正式比较报告**，因此 `AC-06` 的"只有证据支持时才宣称引导模式更优"虽然纪律上被遵守，但**没有可依据的证据**；
- **【推断】** 若在报告层缺失的情况下运行配对实验，会产生一个只有原始数据、没有协议与统计的"实验"，其结论仍需事后重新计算——而 §7.4 要求统计方案在**看结果前**冻结。事后计算存在违反该纪律的风险。

### 7.5 可选方向及取舍

| 方向 | 内容 | 取舍 |
|---|---|---|
| **A. 先出实验 SPEC，再实现报告层** | 按 §7.4 在一个独立 SPEC 中冻结预算、重复次数、统计方法与优越性判据，然后据此实现指标计算 | 最符合 SPEC 的流程要求（"在看结果前冻结"）；但报告层实现会被实验 SPEC 的设计牵引，周期较长 |
| **B. 先补指标计算层，暂不定协议** | 把增长曲线、重复率、连续无增益长度、失败/超时/重放率都算出来并单独报告，优越性判据留待实验 SPEC | 立刻让现有数据可用、可拆解；但不满足"预先冻结"的要求，需要明确声明这些指标**不构成**优越性判据 |
| **C. 解除报告对私有 schema 的耦合** | 先让报告通过 `V2CampaignStore` 公开方法取数，再在其上做指标计算 | 结构更稳；但属于重构，与"审计不顺手改代码"的边界相邻，应作为独立任务 |
| **D. 补齐预算维度** | 把模型调用次数与工具调用次数纳入 Campaign 预算记录 | 单独小步；但会改变 `CampaignBudgetSnapshot` 的契约与既有数据库的兼容性，需评估迁移 |
| **E. A 与 B 并行** | 实验 SPEC 与指标计算层同时推进，指标层先以"可拆解报告"为目标，判据由 SPEC 定 | 折中；但并行时仍需明确"在看结果前冻结"的时点 |

### 7.6 推荐方向及理由

**【建议】** 倾向 **A（实验 SPEC 优先）**，并明确 **C、D 作为独立后续任务**，理由：

1. **`SPEC.md` §7.4 明文要求统计方案"在看结果前冻结"**。若先实现指标再定协议，实现过程本身会引入选择（例如门槛怎么定、连续无增益怎么计数），这些选择在看到数据后做出就违反了该纪律；
2. **第 3 项是硬前置**：在随机基线独立性问题解决前，任何指标计算都无法产出可归因的结论。因此本项的推进顺序应排在第 3 项之后；
3. **C 是重构**，不属于审计范围，且不改变产品语义，可延后；
4. **D 会改变 `CampaignBudgetSnapshot` 契约**，涉及既有数据兼容性，不宜与指标层混做；
5. **B 的风险**在于"产出看起来完整的报告，但它不是优越性判据"——若同时明确标注这一点则风险可控，但仍不如先冻结协议。

**这不构成设计批准。** 预算规模、重复次数、统计方法与优越性判据属于 `SPEC.md` §15 明确列出的待决事项，必须由用户冻结。

## 8. 安全边界与运行默认值

### 8.1 产品 SPEC 要求

- `SEC-02`：**默认拒绝**连接真实生产系统、真实账号或未授权外部服务。
- `SEC-03`：日志和 Artifact **不得保存**密码、私钥、云密钥或**不必要的完整敏感响应**；必须**支持**必要的脱敏与最小化保留。
- `SEC-04`：每个 Episode 结束后验证副作用被隔离或清理；清理失败必须成为**显式测试结果**。
- `SEC-01`：仅针对用户明确授权的合成环境、测试数据和目标运行。
- `FR-REP-01`：Episode 在具有**副作用隔离能力**的 Docker 环境中执行。

### 8.2 当前代码事实

**【事实】**（`E3`）

**网络默认值**

- `SandboxConfig.network_mode` 的类默认值是 `"none"`（`config.py:24`）——满足"默认拒绝"；
- **但 CLI 的 `--ollama-mode` 默认值是 `"host"`**（`v2_cli.py:64`），它把容器网络设为 `"host"`（[:203](src/sandbox/fuzzer/v2_cli.py#L203)、[:246](src/sandbox/fuzzer/v2_cli.py#L246)）。**按默认参数运行会启用宿主网络**。

**凭据防护**

- ✅ `config.py:50-51` 拒绝带凭据或查询串的 endpoint：`raise ValueError("ollama_endpoint must not contain credentials or query data")`。

**脱敏与最小化**

- ⚠️ **存在一处有效的最小化**：`coverage/v2_tool_behavior.py:266-271` 的 "redacted argument-shape contract" 只保留工具参数的**名称与值形状**（`argument_name:value_shape`），不保留参数值。因此覆盖特征不落原始参数值。
- ❌ **未找到通用的日志或 Artifact 脱敏层**：无 redaction/sanitization 模块，无按字段的密钥过滤。`trajectory.jsonl` 保存完整工具结果。

**清理可观测性**

- ✅ 存在清理动作：`cleanup_interrupted`、`_recover_interrupted_work`、`workspace_storage="archive_volume"`、`tmpfs_size="2g"`；
- ❌ `cleanup_confirmed=True` 硬编码（`v2_real_runtime.py:675`），清理失败**无法**出现在 `ExecutionClosure` 中（详见第 6 项）。

**【缺失证据】** `FR-REP-01` 的副作用隔离能力未在真实 Docker 下验证；`tests/integration/` 的 6 个文件中 `grep docker` 无命中。

**【事实】** 缓解因素：Office Workspace V2 是**合成场景**（`build_office_v2_world.py` 建场），且 `AUTHORIZED-EVALUATION-SCOPE.md` 记录了授权范围。因此上述缺口的**当前暴露风险低于其严重性**——但机制层面仍然缺失。

### 8.3 差异为什么重要

**【事实】** `SEC-02` 的语义是"**默认**拒绝"。当前实现是"类默认拒绝、**入口默认允许**"，净效果是默认允许宿主网络。

**【推断】** 宿主网络模式下，容器可访问宿主可达的任何服务。这是刻意的工程便利（连接宿主机 Ollama 是 `--ollama-mode host` 的设计目的），且 `host` 模式正是 `target_judge` 可用的模式（第 4 项）。所以这不是疏忽——但**默认值的方向**与 `SEC-02` 的字面要求相反，需要产品明确裁定。

**【事实】** `SEC-03` 的脱敏缺口在合成场景下风险有限，但 `FR-REP-02` 要求保存"有序的……工具结果"——即完整工具结果是**被设计为**要保存的。若未来场景从合成扩展到包含真实敏感数据，这条路径会成为泄露面。**当前是机制缺失，不是正在发生的泄露。**

**【推断】** `SEC-04` 的清理可观测性问题是三项中最具体的：它不是"缺少一个通用机制"，而是"一个具体的字段总是声明成功"。它与第 6 项的 `cleanup_confirmed` 是同一处代码。

### 8.4 不处理的影响

- `SEC-02`、`SEC-03`、`SEC-04` 保持 `PARTIAL`；`FR-REP-01` 保持 `UNVERIFIED`；
- **【推断】** 影响的时间尺度不同：
  - `SEC-04` 是**现在**就可修的具体缺口（一个字段的取值来源）；
  - `SEC-02` 是**默认值方向**问题，需要产品裁定是"便利优先"还是"拒绝优先"；
  - `SEC-03` 是**机制储备**问题，当前风险低，但随着场景扩展会上升；
- 若对外材料声称"默认拒绝外部连接"或"日志与 Artifact 已脱敏"，将缺少支撑。

### 8.5 可选方向及取舍

| 方向 | 内容 | 取舍 |
|---|---|---|
| **A. 把 `--ollama-mode` 默认改为 `embedded`** | 使默认不启用宿主网络 | 直接满足"默认拒绝"；但 `embedded` 下 `target_judge=None`（第 4 项），晋升路径不可用，改变默认行为会连带影响可用性 |
| **B. 保持默认 `host`，但显式声明** | 不改默认值，在 help 文本、README 与启动日志中明确声明"默认启用宿主网络" | 成本极低、保留便利；但仍不是"默认拒绝"，`SEC-02` 字面上未满足 |
| **C. 增加显式的授权确认开关** | 使用 `host` 模式时要求一个显式的确认参数（如 `--allow-host-network`） | 兼顾便利与"默认拒绝"；但引入新的 CLI 参数与迁移成本 |
| **D. 建立脱敏层** | 在轨迹与 Artifact 写入前增加按字段的密钥/响应最小化过滤，并保留"最小化保留"的配置 | 直接满足 `SEC-03`；但需要定义"什么是敏感"的分类与保留策略，且要与 `FR-REP-02` 的"保存完整工具结果"协调 |
| **E. 复用已有的参数形状化机制** | 扩展 `v2_tool_behavior.py` 的 argument-shape 思路，把最小化原则推广到日志与 Artifact | 复用已验证的机制；但它当前只作用于**覆盖特征**，推广到轨迹需要重新评估重放能力是否受影响 |
| **F. 为清理结果建立显式记录** | 从 Episode 结果读取清理事实，并让清理失败可被记录（与第 6 项 D 相同） | 直接满足 `SEC-04` 的第二半；需要定义"清理失败"的判定与保存位置 |
| **G. 在允许 Docker 时验证隔离能力** | 补一次真实的隔离性验证 | 把 `FR-REP-01` 升级为 `E1`；需要授权与环境 |

### 8.6 推荐方向及理由

**【建议】** 倾向 **F（最优先，已并入第 6 项）+ C + E + G**，理由：

1. **F 是唯一"现在就有明确缺陷"的一项**：`cleanup_confirmed` 恒为真使 `SEC-04` 的可观测性要求无法满足。它成本低、边界清晰，应优先；
2. **C 比 A 更合适**：A 会连带破坏目标保持与晋升（`embedded` 下 `target_judge=None`），代价超出安全默认值本身；C 用一个显式开关实现了"默认拒绝"的意图，同时保留 `host` 模式的可用性；
3. **B 不推荐**：它保留了与 `SEC-02` 字面要求的偏离，且"文档声明"属于 `E4`，不能支撑 `ALIGNED`；
4. **E 优于 D**：仓库里已有一个经过测试的参数形状化机制，把最小化原则推广比新建通用脱敏层更贴近现有设计；但需评估是否影响重放能力（第 5 项）；
5. **G 是唯一能把 `FR-REP-01` 从 `UNVERIFIED` 升级的路径**，需要用户授权。

**这不构成设计批准。** 脱敏策略与"敏感"的定义需要独立 SPEC。

### 8.7 需要用户决定的具体事项

> **决策 1**：`--ollama-mode` 的默认值是否保持 `host`？若是，是否同意在 CLI help、README 与启动日志中**显式声明**默认启用宿主网络？若否，是否采用显式授权开关（C）？
>

>

>
> **决策 4**：是否授权在后续任务中运行真实 Docker 以验证 `FR-REP-01` 的副作用隔离能力？
>
> **决策 5**：当前是否有任何对外材料声称"默认拒绝外部连接"或"日志与 Artifact 已脱敏"？若有，需要按实际实现重新核对。

### 9.3 差异为什么重要

**【事实】** `AGENTS.md` §4 专门警告了"名称不自动等同于产品概念"这一问题，并点名了 `coverage_gain`、`risk_progress` 等名称。本次审计确认这些名称**确实**存在语义落差。

**【推断】** 命名落差的实际危害不是"代码难读"，而是**沟通与验收风险**：一个不熟悉实现的复核者看到 `coverage_gain`、`WeightedSelectionOption`、`independent_uniform_selection` 与 `new_behavior_risk_links`，很可能得出"联合覆盖与加权引导已实现"的结论——而这三者分别是不成立的。第 1、2、3 项的许多争议都源于此。

**【事实】** 两代实现并存本身不是缺陷（V2 是当前主链，旧实现可能仍被其他入口使用），但它使"当前能力"的判定必须依赖调用链分析而非目录浏览——这正是本次审计采用 `grep` 穷举 + 逐处阅读而不是按目录概述的原因。

**【事实】** ruff 基线不通过是一个可核查的工程卫生问题，且成本极低（2 个可自动修复的错误）。

### 9.4 不处理的影响

- 复核成本持续偏高，且沟通中容易被名称误导（具体风险见 9.3）；
- `AGENTS.md` §6 规定的最低检查基线处于不通过状态；
- **【推断】** 若第 1、2、3 项采纳了修正方向，`coverage_gain`、`WeightedSelectionOption`、`build_independent_baseline_brief`、`config/risk-taxonomy.yaml` 这几个名称的处置会**自然改变**——所以本项应在它们定论后再执行，否则可能重复劳动。

### 9.5 可选方向及取舍

| 方向 | 内容 | 取舍 |
|---|---|---|
| **A. 只修 ruff 基线与文档说明** | 修 2 个导入错误；在文档中为语义有落差的名称加说明；不动代码命名 | 成本极低、立刻恢复 `AGENTS.md` §6 基线；但命名落差仍在 |

### 9.6 推荐方向及理由

**【建议】** 倾向 **先 A，其余待前 8 项定论后逐项评估**，理由：

1. **A 无争议且是硬性基线**：`AGENTS.md` §6 要求的最低检查当前不通过，修 2 个测试文件的导入错误成本极低、无行为影响；
2. **B、C、D、E 都依赖前 8 项的决定**：`coverage_gain` 的改名取决于第 1 项选哪个方向；`build_independent_baseline_brief` 与 `config/risk-taxonomy.yaml` 的处置取决于第 1、3 项；报告解耦属于第 7 项。在它们定论前动这些标识，很可能需要返工；
