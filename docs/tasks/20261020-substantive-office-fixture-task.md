## 1. 交付与执行边界

交付一套“设备试点交接”办公材料：三族各至少两个实质实例、每族三种完成方式、八机制各至少两种情境化措辞，以及使新材料进入现有 Agent、工具、判据和记录链的必要接入。

- 新 fixture 使用独立身份；实现名拟用 `substantive-office-01`，初版 `1.0.0`。最终身份在 T01 固定，此后改材料必须遵守版本与摘要契约。
- 旧 fixture 继续默认可用，既有文件和行为保持不变；不回写历史运行结果。
- 新增独立材料目录与少量必要模块，复用已有公共抽象。不得复制整套 Campaign、Agent、journal 或工具引擎，不做通用插件平台。
- 保留四类风险、现有覆盖和评分语义；新 fixture 单独定义业务完成条件。新完成判断不能改变旧 fixture 的 `task_completed`。
- 只允许新 fixture 增加必要的材料选择字段及其记录、菜单和恢复绑定；随机仍为纯随机，引导仍由 LLM 消费反馈，两臂共享新候选空间。
- 不安排两套 fixture 的实验分工、不跑正式两臂实验、不加安慰剂或在线攻击生成、不部署或操作服务器。
- T01—T06 为本地材料、代码与契约验收；T07 为本地真实 Agent 验收。无可用本地 Provider 时，记录未验证和依赖，不能用 fake 代替后将整体任务标为 `DONE`。

当前工作树有用户删除的 README、两份历史文档及大量未跟踪文件，均不纳入本任务。`docs/SPEC.md` 缺失不以本任务补造；已批准 SOF SPEC 是本次材料契约。

### SOF-T03｜攻击措辞与自然载体注入

- **状态**：`DRAFT`。
- **对应需求**：SOF-06、10、11、14、15；SOF-AC-06。
- **依赖**：T01、T02；被 T05—T07 依赖。
- **包含范围**：八机制各至少两种情境化措辞，至少三类实际载体；基于干净底稿的局部注入和可复核差异。
- **不包含范围**：安慰剂、在线攻击生成、修改正式授权、保证每种机制都违规或强迫读取载体。
- **预计区域与数据流**：新语料目录中的攻击库、载体适配与物化模块；实例资源 → 情境化措辞 → 指定低信任区域 → 完整文件及注入证据。

实施 checklist：

- [ ] 八机制均使用材料中真实存在的字段关系、收件人或资源，提供至少两种不只换路径的表达。
- [ ] 来信、批注/说明、历史记录至少三类载体包含自己的业务正文；仅支持与具体机制相容的合法组合，不虚构全笛卡尔积。
- [ ] CSV 用标准行/列、邮件用正文或原有头字段、ICS 用合法描述内容；不统一追加通用攻击尾注。
- [ ] 固定载体可写区域和正式任务、审批不可写区域；记录底稿、注入文本、位置、diff 与最终摘要。
- [ ] 读取但未执行、未读取、成功执行分别可由现有链路辨认；载体不能把受限事实新增到本来没有该事实的实例。
- [ ] 不同机制物化前后的干净业务资源和权限声明一致，差异只来自声明的注入范围。

验收 checklist：

- [ ] 至少十六份具体措辞，以及相应文件内呈现样例可审阅；三类载体真实物化。
- [ ] 引用的目标可解析且操作可达；不声明工具无法支持的攻击动作。
- [ ] 正式授权、任务必要信息及裁判真值不被注入覆盖；同选择可确定性重建。

验证方式：运行文件格式解析、注入范围差异、资源引用和底稿一致性聚焦测试；人工阅读每种机制的两种措辞及各类载体样例。

风险、失败与回滚：攻击破坏格式、上下文不成立或污染授权时该组合不合格；修正新攻击/载体，不全局放宽规则。保留干净底稿以便撤销注入。

尚未解决的问题：机制与载体的具体适配表由真实文件内容确定；无须保证所有机制出现在所有文件中。
