## 1. 目的

本次工作要在不修改产品代码的前提下，整理 `wp2-redteam` 当前代码的真实结构和行为，并逐条对照产品 SPEC，形成可以由用户理解、复核和决策的现状文档。

审计要回答四个基本问题：

1. 输入是什么，经过哪些模块和状态变化？
2. 输出、外部副作用和持久化结果是什么？
3. 风险、行为、联合覆盖以及实验结论由什么证据判定？
4. 失败会发生在哪里，当前有哪些测试或运行证据能够识别它？

本规格只定义审计方法和交付物，不预判当前代码是否符合产品 SPEC，也不包含修复设计。

## 7. 证据等级

每项结论必须标明最高可获得证据等级：

| 等级 | 名称 | 判定条件 |
|---|---|---|
| `E1` | 运行证据 | 在目标环境或可接受的代表性环境中实际观察到，并保存了命令、输入和结果 |
| `E2` | 测试证据 | 自动化测试执行通过，且测试断言能够直接区分该行为是否成立 |
| `E3` | 静态代码证据 | 存在可追踪的调用链和数据流，但本次未实际运行 |
| `E4` | 文档声明 | 只在 README、HANDOFF、LOG、注释或历史计划中声明，尚未由当前代码或运行验证 |
| `E0` | 无可用证据 | 找不到证据，或现有环境不足以判断 |

规则：

- 高等级证据不自动覆盖版本不一致的低等级证据；必须先确认它们针对同一代码基线。
- 测试“运行通过”不等于测试具有判定力；只有直接保护目标行为的断言才计为 `E2`。
- 类名、函数名、字段名和注释只能作为定位线索，不能单独证明产品语义已经实现。
- 历史运行报告必须验证来源、代码版本和完整性；否则最多视为 `E4`。
- 不能执行的 Docker、GPU、远程服务或真实模型路径必须标为未验证，不得用本地模拟结果替代。

## 8. SPEC 合规状态

每条产品要求必须使用以下状态之一：

| 状态 | 含义 |
|---|---|
| `ALIGNED` | 当前行为符合要求，且至少有与结论相称的代码和验证证据 |
| `PARTIAL` | 已有相关结构或部分路径，但尚未完成整个要求 |
| `CONFLICTING` | 当前行为或数据语义与要求直接冲突 |
| `MISSING` | 在审计范围内未找到对应实现 |
| `UNVERIFIED` | 看到了可能的实现，但证据不足以判断是否工作 |
| `NOT_APPLICABLE` | 经用户确认，该要求不适用于本次审计对象或当前阶段 |

`ALIGNED` 不能只依赖 `E4`。如果静态代码看似完整但无法运行或缺少有判定力的测试，应使用 `UNVERIFIED` 或 `PARTIAL`，并说明原因。

每条合规记录至少包含：

- 产品 SPEC 编号与原意；
- 当前代码行为；
- 文件、符号和行号证据；
- 测试、命令或运行产物证据；
- 证据等级；
- 合规状态及判定理由；
- 影响与风险；
- 需要用户决定的问题。

## 9. 审计方法

`AUD-REQ-11`：执行审计时按以下顺序收集证据：

1. 冻结并记录 Git 与环境基线；
2. 清点入口、依赖、目录和主要数据类型；
3. 从 CLI 沿调用关系追踪代表性完整数据流；
4. 分别追踪随机与覆盖率引导策略；
5. 核查持久化 schema、Replay、Artifact 和报告出口；
6. 将测试映射到实际行为要求，识别无断言或弱断言；
7. 在不会修改外部系统的前提下运行获批的本地检查；
8. 建立逐条 SPEC 合规矩阵；
9. 对互相矛盾的代码、测试、文档和历史证据进行交叉核查；
10. 输出事实、推断、未知项和讨论项，不输出未经批准的修复代码。

审计应优先复用现有测试和固定 fixture。是否运行 Docker、下载依赖、调用模型或使用历史服务器归档，必须在 TASK 中单独列明前置条件与副作用。

## 10. 交付物

审计完成后应产生以下文档；准确文件名可在 TASK 中确定，但职责不得混合：

1. **项目地图**：目录、入口、依赖、运行时和模块职责。
2. **数据流与状态模型**：完整 Episode 链路、关键对象、持久化和失败恢复。
3. **策略比较**：随机模式与覆盖率引导模式的共享链路、分叉点和公平性。
4. **SPEC 合规矩阵**：逐条需求的状态、证据和影响。
5. **待讨论问题**：需要用户决定的歧义、冲突、缺失和方案边界。

文档应面向不熟悉代码的用户，首次出现的技术词必须用当前项目中的输入、输出、状态和失败例子解释。图表只在能明显改善理解时使用。

`AUD-REQ-12`：待讨论问题必须按以下结构记录：

1. 产品 SPEC 要求；
2. 当前代码事实；
3. 差异为什么重要；
4. 不处理的影响；
5. 可选方向及取舍；
6. 推荐方向及理由；
7. 需要用户决定的具体事项。

审计阶段可以说明方向，但不得把推荐方向写成已经批准的设计。

## 11. 执行约束与副作用

- 审计以只读检查为主；只允许创建本规格批准的审计文档和任务文档。
- 本地测试可能生成缓存、临时数据库或报告。TASK 必须事先列出允许产生的位置及清理方式，未经确认不得删除用户现有文件。
- 不得调用会修改远程服务器、真实账号、生产数据或未授权外部服务的命令。
- 不得运行来源不明的脚本、二进制文件或历史 Artifact。
- 不得在审计过程中顺手修复代码、测试、命名或文档；所有修复进入后续 SPEC。
- 每个已完成的逻辑文档改动在验证后单独创建 Git 提交，且只暂存该改动涉及的文件。

## 12. 失败与停止条件

遇到以下情况时，暂停相应审计路径并记录阻塞：

- 工作区发生无法归因的新变化，无法确认审计基线；
- 文件需要额外权限且无法安全读取；
- 运行命令可能修改未授权环境或泄露敏感信息；
- 测试依赖缺失且安装会改变环境或扩大授权范围；
- 文档、测试和代码相互冲突，现有证据不能判断真实行为；
- 无法公平比较两种策略的候选空间或预算；
- 发现需要先由用户定义的核心术语或验收口径；
- 审计开始演变成重构、修复或新功能设计。

局部路径被阻塞不代表整个审计失败；应继续完成其他可安全核查的部分，并把阻塞项标为 `UNVERIFIED`。
