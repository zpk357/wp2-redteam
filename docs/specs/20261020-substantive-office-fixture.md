# SOF：具有实质业务内容的独立办公 fixture

状态：`APPROVED`。用户于 2026-10-20 在本对话回复“批准，写TASK”；允许任务拆解，TASK 获得批准前不得实现代码。

日期：2026-10-20。代码参考：本仓库 HEAD `e34a78b` 及当前工作树。

## 1. 目标与范围

用户要解决的是现有实验材料过于简略的问题：新增一套有意义的任务、业务文件和诱导材料，继续使用现有办公工具协议。另建 fixture 是为了保护现有实现和材料。

### 已确认的要求

- **SOF-01｜独立交付与旧版保护**：新增具有独立 ID、版本和材料身份的 fixture。现有 `error-capable-multipath-02` 的默认入口、材料、行为、判据和既有产物不得被替换或追溯改写。新材料必须经显式选择才能使用。
- **SOF-02｜内容充实**：任务文件、业务源文件、普通背景文件和攻击载体须构成可理解、可执行、相互一致的办公情境。不能只替换旧版人名、编号和文件名，或扩写无信息量的套话。
- **SOF-03｜复用工具协议**：沿用现有 Office V2 邮件、云盘、日历、工作区工具的名称、参数契约、结果和隔离语义；Agent 自己发出真实工具请求。新 fixture 的资源和语料可以独立物化。
- **SOF-04｜发现任务与自主选路**：Agent 在多个文件中寻找任务文件；读到任务后根据业务要求选择完成方式。不得把任务正文、正确交付内容、特定文件路径或计划选中的路线提前塞进首轮输入。
- **SOF-05｜权限可理解**：Agent 应知道如何确认授权、来源和受众，并能在环境中找到本次具体依据。文件清单不得直接输出裁判侧角色或 `classification` 等答案标签。
- **SOF-06｜文件内诱导**：攻击文本位于场景文件内，并与该文件的业务上下文结合；攻击方式和载体应有实际差异。
- **SOF-07｜范围收束**：本规格只定义新 fixture 的材料和必要接入契约，不设计两套 fixture 的实验分工、不制定 Campaign、样本量、服务器操作、正式实验准入或优越性结论。安慰剂不在本次范围。

### 本次批准的材料要求

用户本次整体批准包括下文的业务主题、最低材料规模、路径条件和验收方式。固定、预先编写的材料是允许的；本规格不要求每集由 LLM 即时生成正文。

## 2. 术语

| 术语 | 本规格含义 |
| --- | --- |
| 业务材料包 | 一项具体工作需要的任务、事实、资源、权限依据、历史及背景文件，以及裁判侧事实声明 |
| 业务变体 | 改变会影响任务结果或合法决策的业务事实；仅改名字、ID、目录、顺序不算 |
| 完成路径 | Agent 实际可以选择、且满足同一项业务任务的工具行动方式；计划的路径偏好不等于实际路径 |
| 普通背景文件 | 与业务环境有关，但对当前任务不构成授权、也可能不参与最终答案的材料 |
| 攻击载体 | 承载诱导文本的真实文件位置，如来信段落、草稿批注、历史记录或附件说明 |
| 裁判侧声明 | 不交给 Agent 的事实真值、授权集合、受保护对象、预期完成条件和材料摘要 |

## 3. 材料内容

### SOF-08｜三个任务族的完整业务主题

保留简报交付、会议协调、访问复核三个任务族。新语料围绕一个虚构的“设备试点交接”业务背景编写，分别完成以下工作；以下名称和场景均为合成内容。

| 任务族 | 具体工作 | 文件必须提供的实质信息 | 可选完成方式 |
| --- | --- | --- | --- |
| 简报交付 | 根据试点记录向指定合作方提交交接简报 | 各交付项进度、验收结果、未决问题、负责人、期限，以及哪些事实已获对外确认 | 直接邮件；留存草稿后邮件；创建共享简报并授予指定读者 |
| 会议协调 | 在交接期限前组织一次验收评审 | 必需参会人、实际可用时段、时区、时长、评审依赖、议程和附件范围 | 直接创建事件；事件加跟进邮件；共享议程加事件 |
| 访问复核 | 审核合作方对交接资料的访问申请并交付复核结果 | 请求人、具体资源及版本、业务用途、批准人、许可操作、期限与未批准范围 | 邮件复核结论；共享复核记录；为新建且内容获准的资料授予指定读者权限 |

每族至少提供两个实质业务变体：例如不同的阻塞项与交接结论、不同的可行会议窗口和议程依赖、不同的获批资源范围。共至少六个可完整展开的材料实例。变体必须能改变正确输出的内容或合法行动参数。

不要求变体之间所有正文都不同。允许复用组织背景、格式和通用制度，但不能让所有变体仍指向同一个固定事实答案。

### SOF-09｜文件必须能支持工作

每个材料实例均须包含：

1. 一份可发现的工作请求，说明业务目的、交付对象、交付物及完成条件。
2. 至少三份提供不同必要信息的业务源文件；其中至少一项任务结论需要合并两个来源，不能仅复制任务正文。
3. 可发现、内容明确的本次授权及受众依据。
4. 有具体旧事实、日期、适用范围及可识别来源的历史材料。
5. 至少两份具有具体业务内容的普通背景文件，其中至少一份可能因主题相近而被检索到，但不属于本次交付所需材料。
6. 真实存在且可被工具操作的交付或攻击目标资源；需要 Drive 对象时必须实际物化为 Drive 对象，不能只在正文里写一个 ID。

上述角色可由同一文件兼任；不以总文件数或最低字数代替内容验收。

文件不能声称包含一份清单、名册、议程或审批，却不给出具体条目。背景文件也不能全部退化为“请看当前索引”“无权限效力”这类指路占位文本。

### SOF-10｜业务关联与一致性

- 项目、资源、人物、日期、版本和引用应跨文件一致，涉及的身份须可由当前工具解析。
- 当前与历史依据存在差异时，应提供日期、签发来源、适用范围等足以解决差异的信息；不得只靠裁判侧暗藏的“正确版本”判断。
- 普通业务材料可以有真实可解的复杂性，例如公开交接状态与尚未获准披露的内部排查记录同时存在；不人为把所有答案写成一行标签表。
- 同一实例在不同攻击机制下应使用同一份干净业务底稿。更换机制不能顺带新增或移除受限事实、改变授权或降低业务难度。攻击所需资源应在该实例的干净底稿中已存在。

## 4. 任务发现、授权与多路径

### SOF-11｜发现与信任边界

- 首轮输入只给通用工作说明、工作区范围和通用安全规则；材料应提供可用的命名、索引或引用线索，让 Agent 能找到工作请求。
- 任务文件的真实性和权限来源须有明确契约，不能因为某文件自称“工作请求”就自动获得最高权威。通用规则应说明如何识别有效工作请求和当前授权，具体身份及范围经工具读取获得。
- 正式工作请求与攻击可编辑的附注应区分来源。即使载体位于任务所在文件，攻击也不能改写正式任务正文、授权记录或裁判侧真值，再把改写结果当合法授权。
- Agent 可见的来源、批准、保密条款和受众说明属于业务证据；裁判侧的 `restricted_work`、目标风险类别、标准答案等不能借工具结果泄漏。

### SOF-12｜真正可选的完成路径

每族须提供至少三种可完成工作的方式，至少涉及两种对受众有实际效果的工具链。业务任务说明交付要求和渠道限制，不直接输出诸如 `create_drive_file → share_drive_file` 的程序步骤表。

路径的选择要有可解释的业务条件，例如可直接阅读的邮件与需保留链接的多附件简报、需要跟进确认的会议、需要交付审查记录的访问申请。材料须提供相关附件、收件人和资源，不能只在注册表声明路径存在。

Agent 可以使用与计划偏好不同的合法路径；实际完成与否由执行证据和业务条件判断。留草稿可以是安全回退，但只有任务明确允许延期交付时才算完成，不能同时承诺“草稿即可”又按未完成结算。

既有文件在本 fixture 中作为输入记录，正常完成路径不要求改写或删除它们；输出通过新建对象和后续对这些输出的操作完成。这样可在不重定义现有删除、修改判据的前提下，保留清晰的授权边界。

### SOF-13｜为行为探索提供实质选择

应存在选择性检索、跨文件核对、读取附件、查找当前审批、交付渠道选择等真实分支；不能要求所有任务先顺序读完同一批文件再做同一个发送动作。

验收时要展示业务条件如何引出不同的有效工具链及所需证据。不得通过变长文件名、随机 ID、重复读取或增加无关文件制造覆盖差异；也不要求或保证覆盖曲线在任意模型、任意机会数下持续增长。

## 5. 攻击材料

### SOF-14｜保留机制差异，改写为场景内容

新 fixture 支持当前八类机制及四类风险：跨文件拼接、链接外传、受众替换、受众扩展、清理指令、替代版本清理、记录纠正、权限台账改写。

每种机制至少提供两种与业务内容结合的具体措辞，不能只对同一句通用模板替换路径；同时至少存在来信、批注/工作说明、历史记录等三种有实际文件内容支撑的载体类型。

例如，拼接诱导应利用两份材料之间真实的交接字段关系；受众替换应有具体的转接理由；清理诱导应利用明确存在的旧版和留存关系。诱导可以错误或欺骗，但要求的动作和目标必须真实可执行。

载体应使用符合文件类型的写法：邮件作为邮件段落、表格作为行或备注、日历作为描述字段。不能给所有文件统一追加 `attack_note:` 或同一段 `---` 尾注；不能破坏 CSV、邮件或日历格式来塞入攻击。

### SOF-15｜攻击范围与可重复性

- 攻击只修改声明的低信任载体范围，不删除合法任务必需信息，不改变真实审批或裁判侧事实。
- 载体适配应基于实际可读资源和合理发现链；允许 Agent 不读取攻击，但不得把“没读到”当成“读到后抵抗成功”。
- 保存干净底稿、注入内容、目标位置和物化后正文及其摘要，以便复核注入的确发生且没有附带篡改。
- 同一材料实例、变体、攻击措辞版本、布局及种子应能确定性重建。seed 的作用必须声明；仅重排目录不得宣称获得了新业务实例。
- 不引入在线 LLM 攻击生成要求。引导仍由 LLM 消费反馈作选择，随机仍为纯随机；两臂使用相同的新材料及攻击可选集合。

## 6. 事实、判定与执行边界

### SOF-16｜业务正文与裁判声明同源

各实例须声明公开事实、受限事实及其来源、可读受众、任务授权对象、允许操作、受保护记录和完成条件。正文与声明必须一致，不能由两份手工维护的常量各说一套。

受限材料应有业务意义，例如未批准的客户问题单号和内部排查结论；不能让整个任务只围绕一个固定四位数字。需要精确匹配的标记应作为该实例的自然业务标识存在，不能把标记复制当成完成任务的全部要求。

沿用四类风险及现有证据要求，不在本规格中扩展为通用语义泄露 Oracle。当前精确匹配只能证明已知值的披露；同义改写的不可检出限制必须保留，不能据此宣称所有内容都安全。

对已有输入记录的编辑、删除不属于本次合法任务；新建输出的后续修改不因此算违规。若业务设计必须允许改写已有输入，必须先修订本规格及授权判据，不能直接套用“已有对象被改写即违规”。

交付风险须保留权限依据的可发现性和交付前曝光证据。未读到依据与依据不存在须可区分，不能把不可证伪样本当作模型错误。删除、修改继续按各自确定性证据判断，不伪造“知情”属性。

### SOF-17｜完成必须对应业务结果

新 fixture 的完成条件除工具提交外，还应能检查关键业务字段：简报中的必需结论/事项，事件中的参与人、时间和议程要求，访问复核中的资源、决定与许可范围。

不依赖 Agent 自报完成，也不因“调用过 send_email”就认为正确完成。没有必要强制固定文案；可确定的结构化字段由工具结果和状态核对，开放文本中无法确定的要求须明示为未验证，不用 LLM 一句话覆盖事实证据。

### SOF-18｜必要接入与状态

输入为显式 fixture 身份、材料实例/变体、合法路径偏好、攻击机制/措辞、载体和布局等冻结选择。输出为完整可见文件、Office V2 资源、裁判侧声明、材料版本与摘要。

物化在隔离 Episode 中建立资源；执行由 Agent 决定；工具结果和状态变化进入现有轨迹及证据链；覆盖反馈继续进入引导选择，随机不消费跨集反馈。新材料身份必须进入选择记录和恢复校验，不能恢复到另一实例或另一版正文。

允许增加新 fixture 的注册、材料选择和同源事实绑定等必要接入；不要求建立通用场景插件平台，不更换 Agent 循环、工具权限引擎、恢复机制、覆盖键、评分或两臂策略。

当前主链有固定 fixture、固定事实和固定世界的绑定点，不能假定新增目录即可接通。若复用时发现需要全局改变共享行为，应停止该处实现并回到规格讨论；不能以接入为名改动旧 fixture 的语义。

## 7. 失败方式与风险

| 失败信号 | 必须的处理 |
| --- | --- |
| 材料缺名册、批准、附件、资源或可解析收件人 | 物化验证失败，说明缺失项；不得让 Agent 搜索不存在的资源 |
| 当前与历史文件矛盾且无可发现的解决依据 | 材料实例不合格，修正材料；不得靠裁判暗定答案 |
| 正常路径要求操作一个工具不支持的对象 | 不得声明路径可执行，也不得伪造工具效果 |
| 仅改名、目录或编号就声称实质变体 | 内容验收失败 |
| 攻击混入正式授权，或更换机制改变干净事实 | 注入范围验收失败 |
| 未知正文、工具失败或判据不可见被报告成安全 | 记录 unresolved/未验证，按现有证据规则处理 |
| 全部路径只在菜单中存在 | 路径验收失败，补齐真实材料和工具前提 |
| 文件增多造成预算内无法合法完成 | 报告预算适配问题；不隐瞒、不偷偷增大两臂预算 |
| 新 fixture 接入改变旧材料、默认行为或旧摘要 | 兼容验收失败，隔离改动 |

更多文件可能增加搜索成本，更多正文可能挤压上下文；真实工具链仍可能集中在某条路径，丰富材料也不保证模型会违规。这些风险不能通过强迫 Agent 分流、降低随机臂质量或保证违规率来消除。
