## 一、这个项目是什么

**让 AI Agent 的安全测试从"人肉逐案"变成"自动闭环"。**

测试对象是能调用工具的 LLM Agent（读文档、写文件、跑命令、查数据库）。测试方法：
把**不可信内容**（注入指令）放进 Agent 会读到的载体（工具返回值、文档、工作区文件），
看 Agent 是否被诱导越过安全边界——把受限数据泄露给外部、未经授权删除/修改、把
内部材料写进对外交付物。自动化的三个核心件：

1. **链发现（M0）**：从工具集静态推出"源工具→中间工具→Sink"的攻击链（162 条）与
   Sink 站点（run_shell / fetch / 写文件 / SQL）；
2. **差分验证器**：同一任务跑**基线组**（无注入）与**注入组**，Δ 决定效果层级——
   L1 目标链可达 / L2 参数受影响 / L3 效果确认（探针实命中）。对照自发率必须为 0，
   效果才可归因于注入；
3. **双覆盖反馈调度**：每次运行产出六元组 behavior_key / risk_key，按"失败阶段"
   选择下一轮动作（换载体/TPS 修复/换注入字段/变异载荷/升降优先级），调度评分
   六项加权（不用 RL、不让 LLM 每轮调度）。

两条实验线：

- **office 线**（已归档）：仿办公多文件场景，路线可行性验证 + 主实验（两臂/三臂）。
  因场景较重（每集 30-40 万 token）与 content 场景效度问题，按导师方案挂起；
- **agentfuzz 线**（主线，导师方案 ChainFuzzer-Lite）：轻量工具链场景上的最小闭环
  MVP，14 天计划五段，全部交付。

## 二、做了什么（三个阶段）

### 阶段一：office 线——判定可信 + 主实验（11-12 ~ 11-13）

- **通用判定器**：从历史 334 集恢复"三张约束表"（授权表/策略表/保护事实表）100%
  可恢复；265 集与人工 Oracle 全一致；带防篡改测试（改一个授权人就会被发现）；
- **安全自检**：测试系统自身 7 次越权尝试全部被拒、生效 0；
- **两臂主实验**（3 seed × 2 臂 × 8 集）：风险覆盖调度 vs 无反馈对照——
  可归因子集 **R 9 vs C 0**（类型覆盖 4/4 vs 1/4）；
- **文献审计**：覆盖度量已有对手（SafeAudit 等），"覆盖反馈驱动的调度"是空白——
  论文差异化定位确立；
- **TASK-06**：阶段诊断模块（六项三值事实 + 修复账本 R1-R4）接入调度器；
  TPS 载荷变体（登记式三变体轮转）落地。

### 阶段二：转折——效度危机与路线重写（11-14）

- EV-03 验收批发现 content 场景**中性对照自发违规**（3/5 与 5/5）——任务自然路径
  紧贴受限值。批评"加分项"粉饰后按**可归因子集**重算全部主数字（R 9 vs C 0、
  D 15 vs R 9 +67%）；
- 全面审计（P0-P3 + 设计层）发现**路线分裂**：SPEC §13 提过 agentfuzz 但被 §14
  三条理由否决；导师方案逐条回应三条理由（IP 落点不变/主张重定位为增量消融/
  瓶颈转化为阶段反馈信号），裁决 = 完全按导师方案；
- SPEC v0.3 主路线重写（§0 十一节）+ TASK-08~12 立项；office 线封存（其数据与
  判定器保留为附录素材）。

### 阶段三：agentfuzz MVP 全程（11-15，单日完成五段 + 两个追加实验）

- **TASK-08**（第 1-3 天）：沙箱（路径围栏/shell 垫片/受控 fetch/指标库注入）+
  全量轨迹采集 + provider 中立 React 循环 + LangGraph 适配器。修复适配器未绑定
  工具的缺陷（模型看到裸 chat model 时用手写 bash 回答）；
- **TASK-09**（第 4-6 天）：tps_solver（失败回退原任务）；可重复性 **100%（5/5，
  trace_digest 五次逐位一致）**；
- **TASK-10**（第 7-9 天）：scenario_manager / effect_probes（shell/fetch/file 三类
  探针）/ differential_validator。**真 LLM 差分 L3 ×4/4 复现**（基线组零触发/
  注入组命中）；
- **TASK-11**（第 10-12 天）：覆盖键六元组提取 + CoverageDB + 五级阶段诊断
  （injection_not_read → chain_partial → chain_complete → params_affected →
  effect_observed）+ 六项加权调度器（含每链修复上限）；
- **TASK-12**（第 13-14 天）：四臂消融三轮 76 集。第一/二轮揪出两个 harness 缺陷
  （ssrf 回调端点未注册——探针结构性无法命中，而模型其实 100% 跟随了注入；
  修复触发缺口），修复后终版：**4 臂 × 6 集 L3 100%、三类 Sink 全确认、风险覆盖
  1.00、基线自发率 0、~4.9K token/集**；
- **TASK-13**（追加）：预算消融三轮 54 集——判据未通过（A = D = 2/3），但产出
  qwen3.5 鲁棒性轮廓四点（带外抵抗/参数锚定/任务邻近易感/条件门天然抵抗）；
  变异器两轮迭代（门控幸存缺陷实测修复）；
- **payload_mutator**：指令块改写器（业务锚点守卫 + 四种回退），导师"必须"模块
  全清单收官。

### C. 方法论

- **可归因子集口径**：中性对照自发违规的教训 → 归因分层重算，全部主数字换轨；
- **探针可满足性自检**：ssrf 端点未注册导致探针结构性无法命中（模型 100% 跟随
  却被 harness 拒连）——进首轮跑批检查清单；
- **预注册流程**：场景集/预算/模型/判据跑前冻结，三轮消融全程可复现；
- **负结果的规范记录**：TASK-13 判据未通过如实入册（四点鲁棒性轮廓是其产出）。

## 四、诚实的边界（还没证明的）

1. **调度反馈的增量**：agentfuzz 四臂一致是独立集设计的必然（四轮四次证实）——
   有意义的臂间对比需要非独立设计（共享预算池）或更易感的模型；office 线的
   R 9 vs C 0 是现有效证据，但其 deletion/modification 归因补验未完成（条件性）；
2. **payload_mutator 有效性**：正确 harness 下无失败可修，变异器没有获得转化
   机会（需失败率非零的场景/模型）；
3. **泛化**：单一合成场景 × 单一模型（qwen3.5:27b）；多场景/第二模型未做；
4. **延后项**：CodeQL、SQLi 全面支持、共享状态推断、task_generator、复现打包。
